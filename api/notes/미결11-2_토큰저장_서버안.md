# 미결 11-2 토큰 저장 — 서버 쪽 결정안

작성 2026-09-01 · 백엔드 · **제안이지 결정이 아니다.** 11-2 는 「공동」 항목이고
프론트의 PWA·iOS Safari 조사(프론트 W1 3번)가 아직 안 왔다.
기준: `docs/api/공통규약.md` 0절 인증 · `Stage0.md` 1·2절 · `미결.md` 11-2

**이 문서는 `docs/api/` 반영 대상이다.** 프론트 결과와 합쳐 PM 이 본문에 넣는다.

---

## 1. 쿠키 이름 — 분리한다. 경로는 분리하지 않는다

두 토큰은 역할이 다르고 상호 대체 불가다(`공통규약.md`). **한 브라우저에 둘이 동시에
있을 수 있다** — 학부모가 가족 태블릿에서 가입하고 같은 기기를 아이가 쓰는 경우가
정상 흐름이다. 이름이 같으면 나중에 발급된 쪽이 앞의 것을 덮어쓴다.

```
gm_parent   학부모 JWT
gm_child    자녀 JWT
```

**`gm_` 접두사가 필요한 이유** — 쿠키는 **포트를 구분하지 않는다.** `localhost:8000` 에서
설정한 쿠키를 `localhost:3000` 도, 이 머신의 다른 로컬 프로젝트도 같은 jar 로 본다.
접두사 없이 `token` 같은 이름을 쓰면 개발 중에 남의 프로젝트와 충돌한다.

**경로(`Path`)는 분리하지 않는다.** 자녀 토큰이 필요한 엔드포인트가 `/child` 아래에만
있지 않고 `/cards` `/attempts` `/artworks` `/book` `/events` 로 흩어져 있다
(`Stage0.md` 3~7절). 경로로 가르려면 URL 구조를 인증 기준으로 다시 짜야 하는데,
그건 계약을 바꾸는 일이라 값이 비용을 넘지 않는다.

**대신 서버가 엔드포인트마다 어느 쿠키를 읽을지 명시한다.** 지금 목 서버의
`require_parent` / `require_child` 자리가 그대로 그 역할이다.

## 2. SameSite — 배포 도메인 설계에 달렸다. **같은 사이트로 묶는 것을 권한다**

`SameSite` 의 기준은 **site**(스킴 + 등록가능 도메인)이고 **포트는 사이트 구분에 들어가지
않는다.** 그래서 개발 환경 `localhost:3000` ↔ `localhost:8000` 은 크로스 **오리진**이지만
**same-site** 다. `SameSite=Lax` 로 충분하다.

문제는 운영이다.

| 배포 형태 | site 관계 | 필요한 설정 | ITP 영향 |
|---|---|---|---|
| `app.example.com` / `api.example.com` | **same-site** | `SameSite=Lax` | 없음 |
| `example.com` / `api.other.com` | cross-site | `SameSite=None; Secure` | **3rd-party 쿠키로 취급** |

**운영에서 api 를 web 과 같은 등록가능 도메인 아래 두는 것을 권한다.** cross-site 로 가면
`SameSite=None` 이 필요하고, 그 순간 iOS Safari ITP 의 3rd-party 쿠키 제약을 정면으로
받는다 — 자녀 토큰 30일이 그보다 훨씬 일찍 사라질 수 있다. **도메인 설계 하나로 11-2 의
가장 어려운 부분이 사라진다.**

플래그는 이렇게 둔다.

| 속성 | dev | pilot |
|---|---|---|
| `HttpOnly` | ✓ | ✓ |
| `Secure` | **꺼짐** (로컬 http) | ✓ |
| `SameSite` | `Lax` | `Lax` (같은 사이트 배포 전제) |
| `Path` | `/` | `/` |
| `Max-Age` | 자녀 30일 · 학부모 별도 | 같음 |

`Secure` 를 환경으로 가르는 것이 유일한 분기다. `app_env` 로 이미 갈라져 있다.

## 3. CORS — 지금 설정이 맞다

`allow_credentials=True` + 오리진 명시(`cors_origins`)가 이미 들어가 있다
(`app/main.py`). 쿠키를 쓰면 `allow_origins=["*"]` 는 브라우저가 거부하므로 지금 형태를
유지한다. 운영 오리진은 `.env` 로 넣는다.

## 4. 자녀 토큰 30일 — 갱신·폐기

### 갱신: 슬라이딩하지 않는다

30일 고정으로 두고, 만료되면 **접속 코드를 다시 받는다.** 슬라이딩 만료는 기기를 계속
쓰는 한 영구 토큰이 되는데, 자녀 토큰은 탈취 시 영향이 크다(`미결.md`). 한 달에 한 번
학부모가 개입하는 것이 이 제품에서는 비용이 아니라 **가드레일 쪽에 가깝다.**

### 폐기: `children.token_version` 으로 한다

JWT 는 발급 후 서버가 회수할 수 없다. 폐기가 필요한 경로가 셋이다.

1. 접속 코드 재발급 (`POST /parents/children/{id}/access-code`) — 이전 기기의 토큰은 죽어야 한다
2. 자녀 삭제 (`DELETE /parents/children/{id}`) — 즉시 파기 대상에 토큰도 포함된다
3. 학부모의 명시적 요청 (기기 분실 등)

**방법**: `children` 에 `token_version INTEGER NOT NULL DEFAULT 1` 을 두고 JWT payload 에
같은 값을 담는다. 검증 시 DB 값과 대조해 다르면 401. **폐기는 `token_version` 을 1 올리는
것**이고 그것으로 그 자녀의 모든 기기가 한 번에 끊긴다.

Redis 블랙리스트를 쓰지 않는 이유 — 요청마다 어차피 `children` 을 읽어야 하고(닉네임·
`daily_cap`·타임존), 블랙리스트는 TTL 관리와 유실 시 재로그인 폭주라는 운영 부담이 는다.
정수 컬럼 하나가 더 싸다.

**이건 스키마 변경이라 마이그레이션이 필요하다. `/api/v1` 응답은 바뀌지 않으므로
명세 변경은 아니다.**

## 5. 프론트 조사(W1 3번)를 기다리는 것

여기서 서버가 정할 수 없는 것들이다.

- **PWA 홈 화면 추가 시 쿠키가 유지되는가** — iOS 는 홈 화면 앱이 별도 저장소를 쓰던
  시기가 있었다. 유지되지 않으면 **아이가 아이콘으로 들어올 때마다 접속 코드를 다시
  받아야 한다.** 그러면 쿠키 전제가 무너지고 헤더 + 클라이언트 저장소로 가야 한다
- **ITP 가 same-site 배포에서도 만료를 앞당기는가** — 위 2번의 권고가 성립하는지의 근거
- **`Secure` 없이 로컬에서 실제로 붙는가** — 프론트 개발 환경에서 확인 필요

**이 셋이 답해지기 전에는 E-3/E-4(가입·연동)를 만들지 않는다.** 지금 만들면 다시 짠다
(주차계획 W1 「하지 않는 것」).

## 6. 대안 — 헤더 + 클라이언트 저장소

프론트 조사에서 쿠키가 막히면 이쪽이다. 미리 적어둔다.

`Authorization: Bearer` 헤더 + 토큰을 클라이언트가 보관. **`localStorage` 는 XSS 로
바로 털리므로 자녀 토큰 30일에는 맞지 않는다.** 메모리 보관 + 새로고침 시 재교환이
그나마 낫지만, 아이가 앱을 다시 열 때마다 접속 코드를 요구하게 되어 UX 가 무너진다.

**즉 쿠키가 막히면 「30일 토큰」 자체를 재검토해야 한다** — 저장 위치만 바꿔서 해결되지
않는다. 그 경우 짧은 토큰 + 갱신 토큰 구조로 가야 하고, 이는 E-3/E-4 범위를 넓힌다.
