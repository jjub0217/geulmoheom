## 결론: 폴링으로 간다. SSE 는 Stage 0 에서 만들지 않는다

`미결.md` 판단 기준은 *"3초 안쪽이면 폴링으로 충분, 10초를 넘으면 대기 화면 설계가
달라진다"* 였다. **실측은 평균 6.2초 · 최대 8.1초**(`gemini-3.1-flash-lite-image`,
레퍼런스 포함)로 **둘 사이**다. 기준이 자동으로 답을 주지 않으므로 판단이 필요하다.

폴링을 고르는 이유:

- **10초를 넘지 않는다.** 대기 화면을 따로 설계할 구간이 아니다. 가이드 대사 1~2개로
  메울 수 있는 길이다
- **SSE 는 얻는 것에 비해 붙는 것이 많다** — 연결 유지, 프록시·로드밸런서 타임아웃,
  재연결, 모바일 백그라운드 전환 시 끊김 처리. 아이가 6~8초 기다리는 이벤트 **1회**를
  위해 그걸 다 얹을 값이 없다
- 파일럿 규모(N≈10~30)에서 폴링 부하는 문제가 되지 않는다

`Stage0.md` 5절의 SHOULD(SSE)는 **Stage 1 이후로 미룬다.** GM 서사 스트리밍이 들어오면
그때 연결 기반이 필요해지므로 함께 판단하는 것이 맞다.

## 간격·타임아웃 — `Stage0.md` 5절 값이 실측과 맞는다

이미 적혀 있는 값을 실측으로 검증한 결과다. **바꿀 필요 없다.**

| 항목 | 문서값 | 실측 대비 |
|---|---|---|
| 폴링 간격 2초 | 그대로 | 평균 6.2초 → 3~4회면 도착 |
| 타임아웃 15초 | 그대로 | 최대 8.1초의 약 2배. 여유가 적절하다 |
| 15초 초과 시 `fallback=true` | 그대로 | 실측상 거의 발동하지 않을 것 |

## 하나만 더한다 — **첫 폴링을 3초 뒤에 시작한다**

즉시 2초 간격으로 시작하면 **평균 6.2초 동안 확실히 헛도는 요청이 3회** 나간다.
아무것도 못 얻고 서버만 두드린다.

```
POST /attempts 응답(artwork.status = pending) 수신
  → 3초 대기 → GET /artworks/{id}  (첫 시도)
  → 이후 2초 간격, 15초까지
```

첫 지연 3초는 **실측 최소값보다 짧게** 잡은 것이다(최소가 6초대라 3초면 안전하다).
요청 수가 7~8회에서 4~5회로 준다.

## 재시도 — 폴링 실패와 생성 실패를 구분한다

| 상황 | 처리 |
|---|---|
| 네트워크 오류·5xx | 같은 간격으로 계속. 별도 재시도 카운터를 두지 않는다 — 15초 타임아웃이 이미 상한이다 |
| `status = failed` | **즉시 중단.** 폴링을 계속할 이유가 없다. `placeholder_url` 유지 |
| 15초 초과 | 중단. 서버가 `fallback=true` 로 확정하므로 마지막 응답이 기본 에셋을 준다 |

## 파생 요구 — C-1 대사 세트에 「기다리는 동안」이 필요하다

`미결.md` 가 물은 것 중 하나가 *"아이가 기다리는 동안 보는 것 — 가이드 캐릭터 대사로
메울 수 있는 길이인가"* 였다. **6~8초는 대사 1~2개 분량이다.**

그런데 `MVP_PRD.md` C-1 의 대사 세트는 **카드 제시 / 결과 반응 / 되묻기 / 종료 인사**
넷뿐이다. **「삽화 기다리는 동안」이 없다.** W2 C-1 작업에 한 종류를 더해야 한다.
없으면 6~8초 동안 빈 화면이거나 결과 반응 대사가 어색하게 늘어난다.

## 서버가 할 일 (W3 B-3 구현 시점)

- `artworks.status` 를 `pending → ready|failed` 로 옮기는 워커
- **15초 강제 확정** — 초과 시 `status=ready, fallback=true, r2_key=기본 에셋`
- 기본 에셋은 티어별로 미리 R2 에 올려둔다. 실패 시점에 만들 수 없다
