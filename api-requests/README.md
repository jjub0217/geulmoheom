# api-requests — 프론트 → 백엔드 API 수정요청

프론트 개발자가 필요한 API 변경을 **직접 적는 곳**. `docs/`와 달리 PM 소유가 아니다.

```
api-requests/
  open/   진행 중 — 프론트가 여기에 새 요청을 만든다
  done/   완료 — 백엔드가 구현을 머지하며 여기로 옮긴다
```

**`open/`이 비어 있으면 프론트가 기다리는 API가 없다.** 폴더 목록 자체가 현황판이다.

## 흐름

| 순서 | 누가 | 무엇을 |
|---|---|---|
| 1 | 프론트 | `_TEMPLATE.md`를 복사해 `open/NNN-slug.md` 작성 → PR |
| 2 | 백엔드 | 그 PR을 **승인 = 요청 접수**. 불가능·불필요하면 승인 전에 코멘트로 협의 |
| 3 | 백엔드 | 구현 PR에서 파일을 `done/`으로 옮기고 **완료 기록** 채움 |
| 4 | 프론트 | `main` pull → `make contracts` → 타입이 생성되면 **바로 착수** |

## 프론트가 착수해도 되는 시점

파일이 `done/`에 있다는 것만으로 착수하지 않는다. **아래 두 가지가 실제 신호다.**

1. `make contracts`가 성공하고 `web/src/api/types.gen.ts`에 해당 타입이 생긴다
2. 목 서버 또는 스테이징에서 그 엔드포인트가 응답한다

파일은 사람이 옮기는 것이라 틀릴 수 있지만, 위 둘은 기계가 보증한다. **어긋나면 코드가 맞다.**

## 백엔드가 `done/`으로 옮기는 조건

- [ ] 엔드포인트가 목 서버 또는 실제 서버에서 응답한다
- [ ] `/openapi.json`에 반영되어 프론트가 `make contracts`를 돌릴 수 있다
- [ ] 명세가 바뀌었다면 PR 본문에 「명세 변경 요약」을 적었다 (`docs/`는 PM이 반영)
- [ ] 요청 파일의 **완료 기록**에 PR 번호·머지 커밋을 적었다

## 규칙

- **요청 하나에 파일 하나.** 여러 엔드포인트를 한 파일에 묶지 않는다 — 절반만 끝났을 때 상태를 표현할 수 없다
- 번호는 이어서 증가. 재사용하지 않는다
- 거절·보류도 `done/`으로 옮기고 **사유를 남긴다.** `open/`에 남겨두면 현황판이 거짓말을 한다
- 이 폴더는 **요청과 그 처리 상태**만 담는다. 확정된 계약은 `docs/Stage0_API명세.md`와 `/openapi.json`이 진실이다
