# api-requests — 프론트 → 백엔드 API 수정요청

**프론트가 개발하다 막혔을 때** 필요한 API 변경을 직접 적는 곳. `docs/`와 달리 프론트가 직접 쓴다.

```
api-requests/
  open/   대기 중인 요청
  done/   처리됨 (구현·거절·보류)
```

**`open/`이 비어 있으면 프론트가 기다리는 API가 없다.** 폴더 목록 자체가 현황판이다.

## 여기에 넣지 않는 것

- **개발 전에 정하는 설계 결정** (통지 방식, 토큰 저장, 타임존 등) → `docs/api/미결.md`
- **이번 주에 무엇을 할지** → `docs/주차계획/`

이 폴더는 **개발 중에 생기는 요청**만 담는다. 개발이 시작되기 전에는 비어 있는 것이 정상이다.

## 흐름

| 순서 | 누가 | 무엇을 |
|---|---|---|
| 1 | 프론트 | `_TEMPLATE.md`를 복사해 `open/NNN-slug.md` 작성 → `main`에 push |
| 2 | 백엔드 | 읽었으면 머리말의 **`접수`에 날짜를 적는다.** 이견이 있으면 그전에 말한다 |
| 3 | 백엔드 | 구현 후 `done/`으로 옮기고 **완료 기록** 채움 |
| 4 | 프론트 | `main` pull → `make contracts` → 타입이 생성되면 **바로 착수** |

**올렸으면 상대에게 직접 말한다.** 알림 장치가 없다. `/api-check`가 보조할 뿐이다.

## 프론트가 착수해도 되는 시점

파일이 `done/`에 있다는 것만으로 착수하지 않는다. **아래 두 가지가 실제 신호다.**

1. `make contracts`가 성공하고 `web/src/api/types.gen.ts`에 해당 타입이 생긴다
2. 목 서버 또는 스테이징에서 그 엔드포인트가 응답한다

파일은 사람이 옮기는 것이라 틀릴 수 있다. **어긋나면 코드가 맞다.**

## 규칙

- **요청 하나에 파일 하나.** 여러 엔드포인트를 묶지 않는다 — 절반만 끝났을 때 상태를 표현할 수 없다
- 번호는 이어서 증가. 재사용하지 않는다
- 거절·보류도 `done/`으로 옮기고 **사유를 남긴다.** `open/`에 남겨두면 현황판이 거짓말을 한다
- 논의 결과는 **파일 본문에** 적는다. PR도 이슈도 없으므로 이 파일이 유일한 기록이다
- 확정된 계약은 `docs/api/`와 `/openapi.json`이 진실이다 (경계는 `docs/api/README.md`)
