## 1. 30일 토큰은 실제로 30일 사는가

### 1-a. 널리 알려진 「ITP 7일」은 우리와 무관하다

ITP 2.1 의 7일 캡은 **`document.cookie` 로 만든 쿠키**에만 적용된다. WebKit 원문: *"Only cookies created through `document.cookie` are affected by this change."* 서버가 `Set-Cookie` 로 굽는 HttpOnly 쿠키는 대상이 아니다.

### 1-b. 진짜 위협은 IP 휴리스틱이다 — **확실 (WebKit 소스 확인)**

Safari 16.4(2023-04)부터, **서브리소스 응답을 준 서버의 IP** 가 **최상위 프레임 호스트의 IP** 와 앞 절반이 다르면 그 응답의 `Set-Cookie` 를 **7일로 깎는다.**

```
IPv4: 공통 앞 16비트 미만 → 캡
IPv6: 공통 앞 64비트 미만 → 캡
if (isTopLevelNavigation() || !shouldApplyCookiePolicyForThirdPartyCloaking()) return;
  → 서브리소스 요청에만 적용
```

**이 검사는 등록가능 도메인을 아예 보지 않는다. IP 만 비교한다.** (WebKit commit `b0305b1`, 원문 확인)

`app.geulmoheom.app` 에서 `api.geulmoheom.app` 을 부르는 것이 정확히 그 서브리소스 요청이다. **도메인을 맞춰도 IP 가 멀면 30일이 7일이 된다.**

> CNAME 규칙(Safari 14)은 1st-party 서브도메인을 면제한다고 WebKit 공식 표에 있다. **IP 규칙에는 그 면제가 없다.** 둘을 섞어 읽으면 안전하다고 오판하게 된다.

### 1-c. 대응 둘 — 백엔드 몫

**① `api.` 도 Cloudflare 프록시를 태운다.** 두 호스트가 같은 anycast 대역을 받으면 캡을 피한다. **다만 확정이 아니다** — Cloudflare 가 `104.21.x.x` 와 `172.67.x.x` 를 섞어 주므로 대역이 갈릴 수 있다. **배포 후 실측해야 한다.**

**② 슬라이딩 갱신.** 인증된 요청 처리 시 마지막 갱신이 N시간(예: 12h) 이상 지났으면 `Set-Cookie` 를 재발급해 만료를 30일 뒤로 민다. **7일로 깎이더라도 아이가 7일 안에 한 번 들어오면 계속 밀린다.** ①이 실패해도 요구가 실질 충족된다. 서버에 **절대 만료**를 따로 두어 무한 연장을 막는다.

**refresh 토큰은 답이 아니다.** 쿠키에 두면 같은 캡을 받고, `localStorage` 에 두면 HttpOnly 를 포기하는 것이며 ITP 의 script-writable storage 삭제 대상이 된다.

### 1-d. Android Chrome — 문제 없음

수명 캡이 없다. 상한은 400일뿐이라 30일은 무관. 설치된 PWA(WebAPK)는 Chrome 과 저장소를 **공유**한다 (iOS 와 정반대).

## 2. iOS 홈 화면 앱은 Safari 와 쿠키를 공유하지 않는다 — **PM 결정 필요**

**확실.** 쿠키·localStorage·IndexedDB 전부 별도 파티션이다.

```
Safari 탭에서 6자리 접속 코드 입력 → 로그인됨
  → 홈 화면에 추가 → 아이콘 실행
  → 로그인 안 되어 있음. 코드를 다시 넣어야 한다
```

**만 10~12세에게 두 번 입력은 그 자체로 이탈 지점이다.** 온보딩을 **「홈 화면에 추가」 먼저 → 접속 코드 나중**으로 배치해야 한다. E-3/E-4(가입·연동)와 튜토리얼 「나침반 깨우기」(A-6) 설계에 걸린다.

**iOS 26 부터는 매니페스트 없이도 홈 화면 추가가 기본 standalone** 이라 이 문제의 적용 범위가 넓어진다.

- 프론트 대응: `matchMedia('(display-mode: standalone)')` / `navigator.standalone` 으로 모드를 감지해, 브라우저 탭이면 설치 안내를 먼저 띄운다
- **출처 상충 주의**: 일부 문서가 "추가 시 쿠키 1회 복사"를 주장하나 다수 출처가 부정한다. **복사되지 않는다는 전제로 설계하고, 되면 보너스로 볼 것**

## 3. `SameSite=Lax` 와 CORS — 백엔드 안대로 가면 된다

**`Lax` 로 충분하다. POST·PATCH·DELETE 전부 붙는다.** — **확실 (RFC 6265bis draft-20)**

흔한 오해가 "Lax 는 GET 에서만 된다"인데, Lax 의 「top-level navigation + safe method」 조건은 **cross-site 요청을 예외적으로 허용하는 조건**이지 same-site 요청에 부과되는 요구가 아니다. `app.` ↔ `api.` 는 same-site 이므로 모든 메서드에 붙고, 로그인 응답의 `Set-Cookie` 도 정상 저장된다.

**`SameSite=None` 은 쓰지 말 것.** 불필요하고 3rd-party 차단에만 노출된다.

**세 게이트를 구분해야 한다** — 셋 다 통과해야 쿠키가 붙는다.

| 게이트 | 판정 기준 | 우리 경우 |
|---|---|---|
| fetch credentials | **origin**(scheme+host+port) | cross-origin → `credentials: 'include'` 필수 |
| 쿠키 SameSite | **site**(등록가능 도메인+scheme) | same-site → `Lax` 통과 |
| CORS 응답 검사 | 서버 헤더 | 아래 요구사항 |

**`Domain` 미부착(host-only)이어도 `app.` → `api.` 요청에 정상으로 붙는다.** 쿠키 전송은 **요청 대상 호스트**(`api.`)를 보고 판정하지, 페이지가 어느 오리진에서 도는지는 보지 않는다. "host-only 면 서브도메인에 안 간다"는 말은 `app.` 이 그 쿠키를 **자기 요청에** 못 받는다는 뜻이고, 어차피 HttpOnly 라 `app.` 이 볼 일도 없다.

## 4. `__Host-` 접두사 — 붙일 값어치가 있다

**요구 조건이 백엔드 안과 정확히 일치한다** — `Secure` + `Path=/` + `Domain` 미부착. 추가로 바꿀 게 없다.

**얻는 것**: `Domain` 미부착(host-only)은 *내 쿠키가 새어나가는 것*을 막지만, *남이 내 쿠키 이름을 덮어쓰는 것*은 못 막는다. 나중에 `preview.geulmoheom.app` 같은 서브도메인이 생기고 거기가 뚫리면 `Set-Cookie: gm_child=공격자값; Domain=geulmoheom.app` 을 구울 수 있고, 브라우저는 둘 다 전송하며 `Cookie` 헤더에는 이름·값만 실려 **서버가 진짜를 구분할 수 없다**(cookie tossing). `__Host-` 는 이 경로를 브라우저 차원에서 봉쇄한다.

**개발 환경(http)에서는 이름이 갈릴 수 있다.** 사양상 `http://localhost` 는 secure 로 취급되지만(httpwg PR #2759) 구현이 브라우저마다 다르다 — Chromium main 소스는 허용, **Safari 는 여전히 불확실**(WebKit bug #281149 REOPENED).

**프론트 코드에는 영향이 없다.** HttpOnly 라 JS 가 쿠키 이름을 알 필요도 방법도 없다. 이름 분기는 백엔드 내부 문제다. 예외는 e2e 테스트에서 쿠키를 주입·단언하는 경우뿐.

## 5. 개발 환경 함정

- **쿠키는 포트를 구분하지 않는다** (RFC 6265bis §8.5). `localhost:8000` 이 구운 쿠키를 이 머신의 **다른 모든 localhost 앱이 받는다.** 백엔드가 `gm_` 접두사를 붙인 이유가 이것이고, `__Host-` 로도 못 막는다. **개발 계정에 실제 데이터를 넣지 않는다.**
- **schemeful same-site** — 한쪽만 https 로 바꾸면 cross-site 가 되어 쿠키가 아예 안 붙는다. 바꾸려면 양쪽 동시에.
- **`127.0.0.1` 과 `localhost` 를 섞지 말 것.** 다른 호스트이자 cross-site 다.
- **`next.config` 의 rewrites 로 프록시하지 말 것.** 정적 export 는 rewrites·headers·proxy 를 지원하지 않아 **운영에서 안 통한다.** 개발에서 그 트릭을 쓰면 CORS 버그를 배포 후에 처음 만난다.
- (권고) 개발도 mkcert + `app.geulmoheom.test` / `api.geulmoheom.test` 로 맞추면 위 함정 대부분이 한 번에 사라진다. 세팅 30분.

## 6. Cloudflare Pages 프리뷰 배포 — **결정 필요**

`pages.dev` 가 Public Suffix List 에 등재돼 있다(원본 확인). 따라서 프리뷰 URL `<hash>.<project>.pages.dev` 의 등록가능 도메인은 `<project>.pages.dev` 이고, **`geulmoheom.app` 과 cross-site 다.**

**결과: 프리뷰 배포에서 인증이 아예 동작하지 않는다.** 로그인 응답의 `Set-Cookie` 가 저장되지 않고(cross-site 서브리소스 응답에서 Lax 쿠키 set 불가), 기존 쿠키도 전송되지 않는다.

선택지 — ⓐ 프리뷰용 커스텀 서브도메인(`preview.geulmoheom.app`)을 붙인다 ⓑ 프리뷰에서 인증 검증을 하지 않기로 명시한다. **11-5 에서 Cloudflare Pages 를 막 확정했으므로 지금 같이 정하는 게 맞다.**

## 백엔드에게 요구할 것

**쿠키 속성**

| | 운영 | 개발(`http://localhost`) |
|---|---|---|
| 이름 | `__Host-gm_parent` / `__Host-gm_child` | `gm_parent` / `gm_child` |
| `HttpOnly` | ✓ | ✓ |
| `Secure` | ✓ | ✗ |
| `SameSite` | `Lax` | `Lax` |
| `Path` | `/` | `/` |
| `Domain` | **미부착** | 미부착 |
| `Max-Age` | 자녀 30일(2592000) · 학부모 별도 | 동일 |

**CORS — 실제 요청 응답**
```http
Access-Control-Allow-Origin: https://app.geulmoheom.app   # 정확 일치. 와일드카드 불가
Access-Control-Allow-Credentials: true
Vary: Origin
```

**CORS — preflight(`OPTIONS`) 응답에 추가**
```http
Access-Control-Allow-Methods: GET, POST, PATCH, DELETE   # '*' 무효
Access-Control-Allow-Headers: Content-Type                # '*' 무효
Access-Control-Max-Age: 600                               # 미설정 시 기본 5초
```

1. **`allow_origins=["*"]` 를 쓰지 말 것 — Starlette 함정.** `allow_origins=["*"]` + `allow_credentials=True` 면 에러가 나는 게 아니라 **요청 오리진을 그대로 반사한다**(소스 확인). CORS 에러가 안 나서 정상으로 보이지만, 실제로는 **임의의 사이트가 아이 세션으로 API 를 호출할 수 있는 상태**다. 명시 리스트만 쓸 것
2. **`OPTIONS` 핸들러는 인증을 요구하지 않을 것** — preflight 에는 쿠키가 실리지 않는다
3. **예외·500 응답에도 CORS 헤더가 붙는지 확인** — 안 붙으면 프론트 콘솔에 CORS 에러만 보이고 진짜 원인이 감춰진다
4. **로그아웃**: `Set-Cookie: <이름>=; Max-Age=0; Path=/; ...` — 이름·`Path`·`Domain` 유무가 발급 때와 **하나라도 다르면 안 지워진다**
5. **슬라이딩 갱신 구현** (1-c ②)
6. **`api.` 를 Cloudflare 프록시 뒤로 넣고, 배포 후 `dig` 로 `app.`/`api.` 의 A·AAAA 공통 접두 비트를 확인해 공유** — IPv4 ≥16 / IPv6 ≥64 여야 한다 (1-c ①)
7. 인증 응답에 `Cache-Control: no-store` (Cloudflare 가 앞단)

## 확실 / 불확실

**확실** (사양 원문·WebKit 소스·Chromium/Starlette 소스로 직접 확인)
- `document.cookie` 7일 캡은 HttpOnly 서버 쿠키에 적용되지 않는다
- Safari 16.4+ IP 휴리스틱이 등록가능 도메인을 보지 않고 IP 만 비교하는 코드가 WebKit 에 실재한다
- iOS 홈 화면 앱은 Safari 와 쿠키·웹스토리지를 공유하지 않는다
- same-site 이므로 `Lax` 로 모든 메서드에 쿠키가 붙고 `Set-Cookie` 도 저장된다
- ACAO 와일드카드 불가, preflight 응답에도 정확 오리진 + `Allow-Credentials` 필요, preflight 에는 쿠키가 안 실린다
- 쿠키는 포트를 구분하지 않는다
- Starlette `allow_origins=["*"]` + `allow_credentials=True` = 전 오리진 반사
- `pages.dev` 가 PSL 에 있어 프리뷰는 cross-site
- Next 16 정적 export 는 rewrites·headers·proxy 미지원

**불확실 — 추측하지 말고 실측할 것**
- **Cloudflare 가 `app.`/`api.` 에 실제로 어떤 IP 를 주는지. 30일 성패가 여기 달렸다** ← 가장 중요
- WebKit IP 휴리스틱이 2026 년 현재도 같은지 (WebKit 스스로 "heuristic, may change" 명시. 소스에 코드는 살아 있고 완화 근거는 못 찾음)
- iOS 설치 시 "쿠키 1회 복사" 여부 — 출처 상충. **없다고 가정할 것**
- `__Host-` on `http://localhost` 의 Chrome stable·Safari 실제 동작 — 팀 브라우저에서 확인 필요
