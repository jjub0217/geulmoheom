# 아직 정하지 않은 것

**결정할 때 무엇을 고려하는지**를 담는다. 결정이 나면 이 문서에서 지우고 `Stage0.md` 또는 `공통규약.md` 본문에 반영한다.
**언제 정하는지는 `docs/주차계획/`이 정한다** — 여기를 보고 스스로 골라 착수하지 않는다.

**이 문서가 줄어드는 것이 곧 진척이다.**

---

### 11-1. 삽화 도착 통지 — 폴링 vs SSE · **W1**

제안: **폴링 확정, SSE는 Stage 0에서 만들지 않음** (백엔드 서버안 `api/notes/미결11-1_삽화통지_서버안.md`)
**상태: 결정 직전.** 「공동」 항목인데 프론트가 아직 W1을 착수하지 않아 참여하지 못했다. 프론트 합류 시 확인하고 확정한다

- **실측이 기준의 사이에 떨어졌다** — 평균 6.2초·최대 8.1초. "3초 안쪽이면 폴링, 10초 초과면 대기 화면 설계가 달라진다"의 **그 사이**라 기준이 답을 주지 않았다. 10초를 넘지 않으므로 대기 화면을 따로 설계할 구간은 아니라고 판단
- **SSE는 이벤트 1회를 위해** 연결 유지·프록시 타임아웃·재연결·모바일 백그라운드 전환을 다 얹어야 한다. Stage 1 GM 스트리밍과 함께 판단하는 것이 맞다
- **`Stage0.md` 5절의 간격 2초·타임아웃 15초는 실측과 맞다. 바꾸지 않는다** — 이미 적혀 있던 값이 검증된 셈
- **첫 폴링은 3초 뒤에 시작한다.** 즉시 시작하면 평균 6.2초 동안 확실히 헛도는 요청이 3회 나간다. 요청 수가 7~8회 → 4~5회
- **파생 요구 하나가 나왔다 (처리됨)** — "아이가 기다리는 동안 보는 것"을 물었는데, PRD C-1 대사 세트에 **「삽화 대기」가 없었다.** C-1에 MUST로 추가했다 (W2)

- **실측 완료 (2026-09-01, `adr/0006`): 평균 6.2초 · 최대 8.1초** (`gemini-3.1-flash-lite-image` + 캐릭터 레퍼런스). 위 기준의 **3초와 10초 사이**라 어느 쪽으로도 자동으로 결정되지 않는다
- **레퍼런스 이미지가 지연을 두 배로 만든다** — 없이 3.1초, 있으면 8.1초. 그런데 레퍼런스는 뺄 수 없다(B-5 화풍 일관성 + 안전 톤 완화). **8초를 전제로 설계한다**
- 종전 판단 기준: 3초 안쪽이면 폴링으로 충분, 10초를 넘으면 대기 화면 설계가 달라진다
- 아이가 기다리는 동안 보는 것 — 가이드 캐릭터 대사로 메울 수 있는 길이인가
- 폴링 간격·타임아웃·실패 시 재시도 횟수를 함께 정한다

### 11-5. web 배포 형태와 도메인 설계 · **W1** — **11-2보다 먼저 정해야 한다**

제안: **정적 빌드 + api를 web과 같은 등록가능 도메인 아래** (예: `geulmoheom.app` / `api.geulmoheom.app`)

두 갈래에서 독립적으로 같은 지점에 도달했다 — ① 프론트 스택에 Node가 왜 있는지 따라가다 ② 서버가 11-2 쿠키 설계를 짜다.

- **`MVP_PRD.md` 1.5와 아키텍처 2장은 "단일 컨테이너 배포"라고만 하고 그 안에 무엇이 있는지 말하지 않는다.** 스택은 Next.js(Node) + FastAPI(Python) 두 런타임이다
- Next.js App Router는 기본이 서버 렌더링이라 **프로덕션에 Node 서버가 뜬다.** 단일 컨테이너에 둘을 넣을지, 컨테이너를 둘로 할지, `output: 'export'`로 정적 빌드해 Node를 프로덕션에서 없앨지
- **Stage 0에 SSR이 필요한 화면이 있는가** — 태블릿 PWA고 인증은 쿠키, 데이터는 전부 `/api/v1`에서 온다. 서버에서 미리 그릴 것이 안 보인다
- **이것이 11-2의 입력이다.** 정적 배포면 확실히 크로스 오리진이 되고 `SameSite`·CORS 설계가 갈린다
- **도메인 설계가 11-2의 가장 어려운 부분을 없앤다** — api를 web과 같은 등록가능 도메인 아래 두면 정적 배포여도 same-site라 `Lax`를 유지할 수 있고 iOS ITP의 3rd-party 제약을 통째로 피한다. **인프라 결정이므로 대표 몫**
- **프론트(@jjub0217) 의견이 필요하다.** PM·백엔드가 정해 내려보낼 영역이 아니다

### 11-2. 토큰 저장 위치 · **W1**

제안: 자녀·학부모 모두 HttpOnly 쿠키 (0절 인증)

- 자녀 토큰은 **30일 유효**이고 접속 코드 교환으로 발급된다. 탈취 시 영향이 크다
- PWA·iOS Safari의 HttpOnly 쿠키 제약 확인 필요 (홈 화면 추가 시 유지, ITP)
- 두 토큰은 역할이 다르고 상호 대체 불가 — 쿠키 이름·경로를 분리할지
- 크로스 오리진 여부(web:3000 ↔ api:8000)에 따라 `SameSite`·CORS가 갈린다
- **이것이 정해져야 E-3/E-4 가입·연동을 만든다**

### 11-3. 클라이언트 PII 정규식 배급 · **W3** (E-2 구현 시점)

제안: 백엔드가 JSON으로 제공 → 프론트가 로드 (`GET /config/pii-patterns`)

- 엔드포인트를 신설할지, 빌드 타임 상수로 박을지 (패턴이 바뀌면 프론트 재배포가 필요한가)
- 캐시 정책 — 자녀 토큰 없이도 받을 수 있어야 하는가
- **경계**: 프론트 마스킹은 아이에게 주는 즉시 피드백일 뿐, **최종 판정은 항상 서버**다. 프론트를 우회해도 서버에서 막혀야 한다

### 11-4. 자정 기준 — 일일 상한 리셋 · **W3** (A0-5 구현 시점)

제안: 클라이언트 타임존 헤더(`X-Timezone`), 서버 계산 (2절 참조)

- 일일 상한은 **MVP 필수 가드레일**이다. 클라이언트가 보낸 타임존을 그대로 믿으면 **헤더를 바꿔 상한을 우회**할 수 있다
- 대안: 서버 KST 고정 / 자녀 생성 시점에 타임존을 확정해 저장 후 변경 불가
- 밤 11시 50분에 시작한 세션이 자정을 넘길 때의 처리도 함께 정한다
