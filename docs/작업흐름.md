## 2. 최초 1회

```bash
git clone git@github.com:jinioh88/geulmoheom.git
cd geulmoheom
cp .env.example .env        # 키 값 채우기
make db-up                  # Postgres + Redis
```

**GitHub 계정이 여러 개면 `~/.ssh/config` 별칭을 쓴다.** 기본 `git@github.com`은 키를 못 골라 `Permission denied (publickey)`가 난다.

```bash
# @jinioh88 (개인 계정 키가 id_ed25519_personal 인 경우)
git clone git@github.com-personal:jinioh88/geulmoheom.git

# 이미 클론했다면
git remote set-url origin git@github.com-personal:jinioh88/geulmoheom.git
ssh -T git@github.com-personal        # "Hi jinioh88!" 이 떠야 한다
```

**HTTPS + 토큰을 쓰지 않는다.** 토큰이 `.git/config`에 평문으로 남아 `git remote -v` 한 번에 노출된다.

## 3. 어디서 `claude`를 띄우는가 — 가장 중요

Claude Code는 **실행한 위치에 따라 다른 규칙을 읽는다.**

| 실행 위치 | 로드되는 것 |
|---|---|
| 저장소 루트 | 루트 `CLAUDE.md` (제품 결정·페르소나·용어) |
| `api/` 안 | 루트 + **`api/CLAUDE.md`** (원문 로깅 금지, 안전 어휘 등) |
| `web/` 안 | 루트 + **`web/CLAUDE.md`** (`types.gen.ts` 금지, 아이 화면 금지어 등) |

- **PM 작업은 루트에서** — 문서 작업에 개발 규칙은 필요 없다
- **개발 작업은 각자 패키지 안에서** — 특히 스캐폴딩처럼 구조가 한 번에 정해지는 작업
- **`/init`을 저장소 루트에서 실행하지 않는다.** 루트 `CLAUDE.md`는 코드에서 유도할 수 없는 제품 결정 문서다. 패키지 관례는 `web/`·`api/` **안에서** 돌려 각자의 `CLAUDE.md`에 채운다

## 3-1. `@jinioh88`은 세션을 둘 띄운다

PM 모자와 백엔드 모자를 **각각 다른 Claude Code 세션**으로 쓴다.

| 세션 | 띄우는 곳 | 읽히는 규칙 | 만지는 것 |
|---|---|---|---|
| **PM** | 저장소 루트 | 루트 `CLAUDE.md` | `docs/` `landing/` 주차계획 |
| **백엔드** | `api/` 안 | 루트 + `api/CLAUDE.md` | `api/` `infra/` |

세션을 나누면 규칙이 정확히 갈리고 커밋도 자연히 나뉜다. 다만 **두 세션은 같은 워킹 트리를 공유한다.** 여기서 문제가 생긴다.

### 반드시 지킬 것

**`git add -A` · `git commit -am` · `git add .` 를 쓰지 않는다.**
PM 세션이 명세를 고치는 중에 백엔드 세션이 `git commit -am` 하면 문서 변경이 코드 커밋에 딸려 들어간다. 우리가 막으려던 바로 그 일이 자동으로 벌어진다.

```bash
# PM 세션
git add docs/ && git commit -m "명세: /cards/next 에 remaining_today 추가"

# 백엔드 세션
git add api/ && git commit -m "목 응답 서버 (주차계획 W1)"
```

**나머지 넷**

- 커밋 직전 `git status`로 의도하지 않은 파일이 섞였는지 본다
- push 전 `git pull --rebase` — 다른 세션이 먼저 올렸을 수 있다
- **개발 서버는 백엔드 세션에서만** 띄운다 (`make dev-api`). 양쪽에서 띄우면 포트 8000이 충돌한다
- 한 파일을 두 세션이 동시에 만지지 않는다. 겹치는 곳은 `api-requests/`와 루트 설정 파일이다
- **주차 진척은 각자 `tasks/`에 체크한다.** `docs/주차계획/`의 「진행 현황」은 `/progress-week`이 갱신하므로 손으로 고치지 않는다

`git worktree`로 물리적으로 나누는 방법도 있지만, 워크트리마다 다른 브랜치가 필요해서 `main` 직접 push 체제와 맞지 않는다.

## 3-2. 개발자는 무엇부터 보는가

문서가 여럿이라 헷갈리기 쉽다. **층위가 다르다 — 중복이 아니다.**

| 순서 | 문서 | 무엇 |
|---|---|---|
| 1 | **`docs/주차계획/W1.md`** | **이번 주에 할 일.** 담당·선행·완료 조건. 여기서 시작한다 |
| 1-1 | `api/tasks/W1.md` · `web/tasks/W1.md` | **자기 진척 체크리스트.** 주 시작에 `/my-week`으로 각자 만든다. 계획이 아니라 진척이다 |
| 2 | `docs/api/` | **계약 사양.** `공통규약.md` + `Stage0.md`가 "이대로 만들라"의 기준. 할 일 목록이 아니다 |
| 2-1 | `docs/api/미결.md` | **아직 안 정한 것**과 판단 기준·결정 시점. 이 문서가 줄어드는 것이 진척이다 |
| 3 | `api-requests/open/` | **개발 중** 프론트가 올린 API 요청. 개발 시작 전에는 비어 있는 것이 정상이다 |
| 참조 | `docs/MVP_PRD.md` | 왜 그렇게 만드는가. 3장이 기능 상세, 8장이 마일스톤 |

**아직 안 정해진 설계 결정**(통지 방식, 토큰 저장, 타임존 등)은 **`docs/api/미결.md`**에 판단 기준·결정 시점과 함께 있다. 언제 정하는지는 주차 계획이 정한다 — 그 문서를 보고 스스로 골라 착수하지 않는다.

## 3-3. 큰 작업은 세션을 나눈다

**한 세션에서 하루치를 다 하려 하지 않는다.** 컨텍스트가 늘어지면 Claude가 앞서 정한 것을 놓치고, 규칙 위반(원문 로깅, `types.gen.ts` 수정)이 뒤로 갈수록 늘어난다.

`/my-week` 이 만든 `tasks/W<n>.md` 의 **하위 체크박스 하나 = 세션 하나**로 잡는다.

```bash
cd api && claude
> tasks/W1.md 의 1번 첫 하위 항목을 해줘.
# 끝나면 커밋 → 세션 종료 → 새로 띄운다
```

세션 안에서만 쓰는 임시 단계 목록은 Claude가 알아서 관리한다. **문서로 만들지 않는다** — `주차계획` → `tasks/` 위에 층을 하나 더 얹으면 세 문서가 갈라진다.

### push 할지 말지

| 상황 | 어떻게 |
|---|---|
| 하위 단계 하나를 끝냈고 `main`이 안 깨진다 | **커밋 + push** |
| 항목이 반쯤 됐고 지금 올리면 `main`이 깨진다 | **커밋만. push 보류** — 작업은 로컬에 안전하다 |
| 이틀 넘게 걸린다 / 원격 백업·중간 공유가 필요하다 | **작업 브랜치**를 판다 |

**단계마다 브랜치를 파지 않는다.** 리뷰어가 없어 브랜치→머지가 순수 의식이 되고, 하루에 몇 번씩 하면 리듬만 끊긴다. 브랜치는 위 셋째 줄일 때만이다.

```bash
git switch -c work/api-scaffold      # 이틀 넘는 작업만
# ... 여러 세션에 걸쳐 커밋 ...
git switch main && git merge --ff-only work/api-scaffold && git push
git branch -d work/api-scaffold
```

## 4. 시나리오

### PM — 이번 주차 계획을 세운다

주가 시작될 때 가장 먼저 하는 일이다. **이걸 건너뛰면 두 사람이 각자 다른 것을 만든다.**

```bash
cd geulmoheom && git pull && claude      # ← 루트에서
```
```
> /plan-week                  # 인자를 비우면 다음 주차를 스스로 판단한다
```

주차 번호는 **`MVP_PRD.md` 8장 「주차」 열**에서 온다. 지금이 몇 주차인지 셀 필요 없다 — 명령어가 `docs/주차계획/`을 보고 제안한다. 건너뛰거나 되돌아갈 때만 `/plan-week W3` 처럼 명시한다.

명령어가 이 순서로 진행한다.

0. **이미 그 주차 계획이 있으면 덮어쓰지 않는다.** 차이만 보고한다 —
   「진행 현황」 표와 PM 체크박스는 진척 기록이라 절대 날리지 않는다
1. **진척 보고** — `백로그.md`·PRD 8장·9장·`검증가설_성공지표.md`·`docs/api/미결.md`를 읽고,
   `ls web api`·`git log`로 **말이 아니라 실제로** 무엇이 됐는지 확인한다
2. **범위 초안** — 항목 · 코드 · 담당 · 선행 · 완료 조건 · 크기(S/M/L) 표
3. **과부하 지적** — 2인 팀에 과하면 그렇다고 말하고 덜어낼 후보를 제안한다
4. **PM 확인** ← 여기서 멈춘다. **무엇을 하고 무엇을 미룰지는 PM의 결정이다**
5. 확인 후 `docs/주차계획/W1.md` 작성 (범위·담당·선행·완료 조건·「하지 않는 것」·「진행 현황」 빈 절)

```bash
git add docs/주차계획/ && git commit -m "W1 주차 계획" && git push
```

**`api/tasks/`·`web/tasks/`는 PM이 만들지 않는다.** `web/`은 프론트 소유다.
**두 사람에게 계획 링크를 보내며 "`/my-week W1` 을 돌려라"고 함께 알린다** — 알림 장치가 없다.
`@jinioh88` 본인도 백엔드 세션에서 따로 돌려야 한다. 모자가 다르다.

**계획을 세울 때 지켜지는 것**

- **범위는 지어내지 않는다.** 모든 항목이 `백로그.md`의 코드(A0-2, E-3, F-3…)로 추적된다.
  백로그에 없는 것을 넣으려면 **`비전.md` 4장 질문 5개**를 먼저 통과해야 한다
- **「하지 않는 것」 절을 비우지 않는다.** 뺀 것과 이유를 적지 않으면 범위가 조용히 늘어난다
- **가용량은 2인분이 아니다.** `@jinioh88`의 PM 업무가 백엔드 시간을 깎는다
- **완료 조건은 검증 가능하게.** "구현한다"가 아니라 "무엇이 되면 끝인가" —
  가능하면 기계가 판정하는 것으로 (`make contracts` 성공, 테스트 통과, 응답 확인)
- **담당이 「공동」인 항목은 양쪽 「작업 쪼갬」에 모두 넣는다.** 한쪽에만 있으면 나머지 쪽 몫은
  담당자가 없어 조용히 빠진다. "결정 참여"라고만 쓰지 말고 각자 무엇을 맡는지 갈라 적는다

**주 중에 계획이 틀어지면 문서를 고친다.** 실제와 어긋난 채 방치하면 계획 문서가 죽고,
그다음 주부터 아무도 안 본다. `MVP_PRD.md` 8장이 상위이므로, 어긋남이 주차를 넘어가면 8장도 함께 고친다.

### PM — 하루를 연다 (5분)

PM 세션에서 아침마다 돌린다.

```bash
git pull
git log -p --since=yesterday        # 상대가 무엇을 했는지 아는 유일한 경로
```
```
> /progress-week W1
> /api-check
```

`/progress-week`이 각 패키지 `tasks/`를 읽어 계획의 「진행 현황」을 갱신하고, **막힌 것**(선행 미완으로 후속 대기)과 **계획 이탈**(계획에 없는 항목이 `tasks/`에 생김)을 함께 짚는다. 갱신됐으면 커밋한다.

```bash
git add docs/주차계획/ && git commit -m "W1 진행 현황 갱신" && git push
```

`/api-check`에서 특히 볼 것은 **`접수`가 빈 항목**이다. 프론트가 올렸는데 백엔드(본인)가 아직 읽지 않은 것이고, 방치하면 프론트가 조용히 막혀 있다.

### PM — 문서를 고친다

프론트는 `docs/`를 수정하지 못한다. `api-requests/`에 올리거나 말로 전하고, **반영은 PM 몫이다.**

```bash
cd geulmoheom && git pull && claude      # ← 루트에서
```
```
> api-requests/open/001 읽고 docs/api/Stage0.md 4절에 반영해줘.
  용어사전 아이 화면 열 확인하고.
```
```bash
git add docs/
git commit -m "명세: /cards/next 에 remaining_today 추가 (api-requests/001)"
git push
```

**경로를 명시해서 `git add` 한다** (3-1장). 백엔드 세션이 동시에 코드를 만지고 있다.
**문서 반영은 언제나 코드와 별도 커밋**이다. 같은 사람이라 섞을 수 있지만, 섞이면 "이 명세는 왜 바뀌었나"를 못 찾는다.

### PM — 새 요청을 거른다

기능 추가 요청이 들어오면 PM 세션에서 그대로 던진다. 루트 `CLAUDE.md`가 읽혀 있으므로 Claude가 자동으로 **`비전.md` 4장 질문 5개**에 비춰보고, 하나라도 "아니오"면 먼저 알린다. 5장 「하지 않을 것」에 해당하면 이유와 대안을 낸다.

통과했다면 순서가 있다.

1. `백로그.md`에 항목으로 등록 (코드 부여)
2. 새 말이 나왔으면 `용어사전.md`에 먼저 등록
3. 그다음 주차 계획에 넣는다

**이 순서를 건너뛰면** 코드·문서·아이 화면에서 서로 다른 말이 굳고, 백로그에 없는 일이 계획에 들어온다.

### PM — 주를 닫는다

```
> /progress-week W1
> docs/주차계획/W1.md 의 완료 판정 항목을 실제 저장소 상태와 대조해줘.
```

**체크박스를 믿지 말고 기계로 확인한다** — `make dev`, `make contracts`, CI `all-green`. 어긋났으면 계획 문서를 고치고, 어긋남이 주차를 넘어가면 `MVP_PRD.md` 8장도 함께 고친다.

그다음 `/plan-week W2` 로 다음 주를 연다.

### PM만 지는 책임

| | 왜 PM인가 |
|---|---|
| **`docs/` 전부** | 프론트는 못 고친다. 반영이 막히면 두 사람이 다른 문서를 본다 |
| **용어사전 관문** | 새 말은 사전에 먼저. 안 하면 코드·문서·화면에서 다른 말이 굳는다 |
| **비전 4장 게이트** | 기능 추가를 거르는 유일한 장치다 |
| **주차 계획** | 백로그와 실제 작업을 잇는 사람이 PM뿐이다 |

## 5. 관통하는 규칙

| 규칙 | 왜 |
|---|---|
| 올렸으면 **말한다** | `api-requests/`는 기록이지 알림이 아니다. `/api-check`가 보조할 뿐 |
| `main`에 반쯤 된 것을 올리지 않는다 | 공용 작업대다. `api`가 깨지면 프론트의 `make contracts`가 실패한다 |
| **파일 상태 ≠ 실제 상태** | `done/`은 사람의 주장, `make contracts` 성공은 기계의 보증. 어긋나면 코드가 맞다 |
| 커밋 메시지에 **「명세 변경:」** 줄 | PR 본문도 이슈도 없다. 커밋 메시지가 유일한 기록이다 |
| 논의 결과를 **파일 본문에** 적는다 | 말로 정한 것도 적지 않으면 3주 뒤 근거가 사라진다 |
| 커밋 전 Claude에게 `git diff` 검토 요청 | PR 리뷰의 대체품 중 가장 싸다 |
| 하루 시작에 `git log -p --since=yesterday` | 상대가 무엇을 했는지 아는 유일한 경로 |
| **하위 체크박스 하나 = 세션 하나** | 한 세션에서 크게 하면 컨텍스트가 늘어져 규칙 위반이 뒤로 갈수록 늘어난다 |
| 진척은 **자기 패키지 `tasks/`**에 체크한다 | 한 파일을 둘이 고치면 `main` 직접 push 체제에서 push 거부가 잦다 |
| **할 일은 주차 계획에서만 고른다** | `docs/api/미결.md`도 `api-requests/`(요청)도 할 일 목록이 아니다 |
| 주차 계획이 실제와 어긋나면 **문서를 고친다** | 방치하면 계획 문서가 죽는다. 어긋남이 주차를 넘어가면 PRD 8장도 함께 |
| **`git add -A` · `commit -am` 금지** | `@jinioh88`이 두 세션을 띄운다. 상대 세션 작업이 딸려 들어간다 |

## 6. 슬래시 명령어

`.claude/commands/` 에 있다. 저장소에 커밋되어 두 사람 모두 쓴다.
**무엇을 어떻게 하는지는 각 명령어 파일이 진실이다.** 여기는 언제 누가 쓰는지만 적는다.

| 명령 | 누가 | 언제 |
|---|---|---|
| `/plan-week` | PM | **주 시작** — 이번 주 범위를 정한다 |
| `/my-week` | 개발자 각자 | **주 시작** — 계획에서 내 몫을 뽑는다 |
| `/progress-week` | PM | **매일** — 진행 현황을 모은다 |
| `/api-check` | 누구나 | **막혔을 때** — 요청 현황과 착수 가능 여부 |

인자는 주차 번호(`W1`). `/plan-week` 은 비워도 된다 — 다음 주차를 스스로 판단한다.
`/my-week` 은 **자기 패키지 안에서** 실행한다. 역할을 경로로 판별하기 때문이다.

**이름에 `-week` 접미어를 둔 이유** — 짧은 `/plan` 은 Claude Code 내장 plan mode와 겹쳐 가려진다.
`/status`·`/progress` 도 같은 위험이 있어 피했다. **새 명령어를 만들 때 짧고 흔한 이름을 쓰지 않는다.**
