## 3. 어디서 `claude`를 띄우는가 — 가장 중요

Claude Code는 **실행한 위치에 따라 다른 규칙을 읽는다.**

| 실행 위치 | 로드되는 것 |
|---|---|
| 저장소 루트 | 루트 `CLAUDE.md` (제품 결정·페르소나·용어) |
| `api/` 안 | 루트 + **`api/CLAUDE.md`** (원문 로깅 금지, 안전 어휘 등) |
| `web/` 안 | 루트 + **`web/CLAUDE.md`** (`types.gen.ts` 금지, 아이 화면 금지어 등) |

- **PM 작업은 루트에서** — 문서 작업에 개발 규칙은 필요 없다
- **개발 작업은 각자 패키지 안에서** — 특히 스캐폴딩처럼 구조가 한 번에 정해지는 작업
- **`/init`을 저장소 루트에서 실행하지 않는다.** 루트 `CLAUDE.md`는 코드에서 유도할 수 없는 제품 결정 문서다. 패키지 관례는 `web/`·`api/` **안에서** 돌려 각자의 `CLAUDE.md`에 채운다

## 3-1. `@jjub0217`은 세션을 셋 띄운다

모자마다 **다른 Claude Code 세션**을 쓴다.

| 세션 | 띄우는 곳 | 읽히는 규칙 | 만지는 것 |
|---|---|---|---|
| **PM** | 저장소 루트 | 루트 `CLAUDE.md` | `docs/` `landing/` 주차계획 |
| **백엔드** | `api/` 안 | 루트 + `api/CLAUDE.md` | `api/` `infra/` |
| **프론트** | `web/` 안 | 루트 + `web/CLAUDE.md` | `web/` |

```bash
claude -n gm-pm      # 저장소 루트
claude -n gm-api     # api/ 안
claude -n gm-web     # web/ 안
```

**`-n` 을 빼지 않는다.** 안 붙이면 이름이 「디렉터리명 + 랜덤 접미어」로 자동 생성되는데, 세션 간 전달(아래)에서 **그 이름이 곧 주소**다. 2026-09-06에 두 번 물렸다 — 세션이 재시작되며 이름이 바뀌어 전달이 실패했고, 목록에 `api-b2` 처럼 **다른 프로젝트의 `api/` 세션과 구분되지 않는 이름**이 섞여 어느 쪽인지 알 수 없었다.

세션을 나누면 규칙이 정확히 갈리고 커밋도 자연히 나뉜다. **한 사람이 쓴다고 해서 한 세션으로 합치지 않는다** — 규칙이 섞이면 `web/` 세션에서 명세를 고치고 `api/` 세션에서 화면 문구를 정하는 일이 생긴다. 다만 **세 세션은 같은 워킹 트리를 공유한다.** 여기서 문제가 생긴다.

> **세 세션이 한 트리를 공유한다.** 스테이징이 섞일 수 있는 짝이 3쌍이고, 모자가 셋이어도 사람은 하나라 「상대에게 물어본다」가 안 통한다 — **`git status`로 직접 확인하는 것 말고 방법이 없다.**

### 세션끼리 말을 주고받는다

**세션은 서로에게 메시지를 보낼 수 있다.** 사람이 옮겨 적지 않아도 된다.

- `ListAgents` — 지금 떠 있는 세션 목록. **이름이 주소다**
- `SendMessage` — 그 이름으로 보낸다

받은 세션은 **자기 다음 턴에 깨어나 스스로 작업하고 답을 보낸다.** 지시가 아니라 실제로 일이 돈다 — 2026-09-06에 백엔드 세션이 PM의 `__Host-` 제안을 받아 검토·문서 반영·커밋까지 하고 회신했다.

**쓸 만한 흐름**

| | |
|---|---|
| 개발 세션 → PM | 「이거 `docs/` 반영이 필요하다」 — 명세 변경, 미결 결정, PRD와 어긋난 것 |
| PM → 개발 세션 | 결정된 것을 내려보낸다. 미결 확정, 주차 범위 변경, 다른 세션이 올린 질문의 답 |
| PM → 개발 세션 | `notify_when_idle` 로 **끝났을 때 한 번 알림**을 구독한다 |
| PM → 전 세션 | **브랜치를 파기 전에 길을 비운다** — 아래 |

**브랜치 조율은 PM 몫이다.** 개발 세션이 이틀 넘는 작업으로 브랜치가 필요하면(3-3), `git switch` 가 **트리 전체를 바꿔 나머지 두 세션의 파일을 갈아버린다.** 파기 전에 PM이 다른 세션들의 작업을 커밋시켜 정리하고, 브랜치로 갔다는 것과 돌아왔다는 것을 알린다. **세션은 자기가 어느 브랜치에 있는지 모른 채 계속 일한다** — 알려주는 장치가 없다.

**안 되는 것 — 여기가 중요하다**

- **PM은 지시는 하지만 승인은 못 한다.** 개발 세션이 권한 프롬프트를 만나면 **사람에게** 뜬다. PM 세션이 대신 눌러줄 수 없고, **눌러주려고 그 작업을 PM 세션에서 대신 하는 것은 금지다** — 사람이 내린 권한 결정을 우회하는 것이다. 결국 터미널 셋을 사람이 봐야 한다
- **두 세션에 동시에 일을 던지지 않는다.** 워킹 트리가 하나다. 둘이 동시에 편집·스테이징·커밋하면 아래 「반드시 지킬 것」의 두 구멍이 그대로 터진다. **하나 끝나고 다음**
- **보냈다고 된 게 아니다.** 비동기다 — 응답을 기다리며 멈추지 않는다. 확인은 **커밋과 파일로** 한다. 5장의 *"파일 상태 ≠ 실제 상태"*가 그대로 적용된다
- **대표 결정은 이 경로로 오지 않는다.** PM 세션은 `@jjub0217`의 PM 모자다. 「대표 몫」 넷(1장)은 여전히 **사람 대 사람**이다 — 세션끼리 아무리 주고받아도 도메인은 등록되지 않는다

**PM 세션은 조율자이지 관리자가 아니다.** 결정을 전달하고 결과를 모으는 것까지가 범위다.

### 반드시 지킬 것

**`git add -A` 와 `git commit -am` 을 쓰지 않는다. 어느 디렉터리에서든.**
둘 다 **현재 위치와 무관하게 워킹 트리 전체**를 담는다. PM 세션이 명세를 고치는 중에 백엔드 세션이 `git commit -am` 하면 문서 변경이 코드 커밋에 딸려 들어간다. 세션이 셋이면 `web/`의 반쯤 된 작업까지 함께 담긴다.

**`git add .` 는 현재 디렉터리 하위만 담으므로 패키지 안에서는 안전하다.** 저장소 루트에서만 쓰지 않는다.

```bash
# 백엔드 세션 — api/ 안에서. cd .. 할 필요 없다
git add .                    # api/ 하위만 담긴다
git commit -m "목 응답 서버 (주차계획 W1)"

# 다른 폴더도 함께 담아야 하면 경로를 명시한다 (git 은 저장소 루트 기준으로 받는다)
git add . ../infra

# PM 세션 — 루트에서. 여기서는 `.` 를 쓰지 않는다
git add docs/ && git commit -m "명세: /cards/next 에 remaining_today 추가"
```

**커밋은 나눠도 push는 공유된다 — 두 번째 구멍**

위의 `git add` 규칙은 **스테이징** 오염을 막는다. 그런데 세 세션이 같은 `main`을 쓰므로, **한 세션이 `git push`하면 다른 세션이 로컬에 쌓아둔 커밋까지 함께 올라간다.** 커밋을 아무리 깔끔히 나눠도 이건 안 막힌다.

실제로 세 번 일어났다 — 2026-09-01에 두 번(PM 세션의 문서 커밋 3개가 백엔드 push에 딸려 감), 09-06에 한 번(백엔드 커밋 `16c9afa`가 PM push에 딸려 감). 전부 완성된 커밋이라 문제는 없었지만, **반쯤 쓴 것을 커밋해 뒀다면 그게 `main`에 올라갔을 것이다.** `main`이 항상 돌아가야 하는 체제에서 이건 그냥 사고다.

```bash
git log origin/main..HEAD    # push 전에 무엇이 올라가는지 본다
```

**다른 세션의 커밋이 보이면 `git show`로 완성 여부를 확인한다.** 내 것만 올리려고 브랜치를 파는 건 과하다 — 대개는 그 커밋도 `main`이 목적지다.

**전부 자기 커밋이라 "내가 올린 건가"로 그냥 넘어가기 쉽다.** 물어볼 상대가 없다. **`git log origin/main..HEAD`를 눈으로 읽는 것이 유일한 장치다.**

**나머지 다섯**

- 커밋 직전 `git status`로 의도하지 않은 파일이 섞였는지 본다
- push 전 `git pull --rebase` — 다른 세션이 먼저 올렸을 수 있다
- **개발 서버는 백엔드 세션에서만** 띄운다 (`make dev-api`). 양쪽에서 띄우면 포트 8000이 충돌한다
- 한 파일을 두 세션이 동시에 만지지 않는다. **파일 소유가 갈려 있어 겹칠 일이 거의 없고, 겹치는 곳은 루트 설정(`CLAUDE.md`·`Makefile`·`.github/`)뿐이다** — 그건 PM 세션 몫이다
- **주차 진척은 각자 `tasks/`에 체크한다.** `docs/주차계획/`의 「진행 현황」은 `/progress-week`이 갱신하므로 손으로 고치지 않는다

`git worktree`로 폴더를 물리적으로 나누는 방법도 있다. **안 쓴다** — 워크트리마다 다른 브랜치가 필요해 `main` 직접 push(`adr/0004`)와 맞지 않고, `make contracts`가 api를 띄워 web에 타입을 쓰므로 두 패키지가 한 트리에 있어야 한다. 폴더 수만큼 `node_modules`·`.venv`도 생긴다.

| 3 | ~~`api-requests/open/`~~ | **휴면** (2026-09-06~). 요청자와 담당자가 같은 사람이 되어 왕복이 성립하지 않는다 |
| 참조 | `docs/MVP_PRD.md` | 왜 그렇게 만드는가. 3장이 기능 상세, 8장이 마일스톤 |

**아직 안 정해진 설계 결정**(통지 방식, 토큰 저장, 타임존 등)은 **`docs/api/미결.md`**에 판단 기준·결정 시점과 함께 있다. 언제 정하는지는 주차 계획이 정한다 — 그 문서를 보고 스스로 골라 착수하지 않는다.

## 3-3. 큰 작업은 세션을 나눈다

**한 세션에서 하루치를 다 하려 하지 않는다.** 컨텍스트가 늘어지면 Claude가 앞서 정한 것을 놓치고, 규칙 위반(원문 로깅, `types.gen.ts` 수정)이 뒤로 갈수록 늘어난다.

`/my-week` 이 만든 `tasks/W<n>.md` 의 **하위 체크박스 하나 = 세션 하나**로 잡는다.

```bash
cd api && claude -n gm-api
> tasks/W1.md 의 1번 첫 하위 항목을 해줘.
# 끝나면 커밋 → 세션 종료 → 새로 띄운다
```

세션 안에서만 쓰는 임시 단계 목록은 Claude가 알아서 관리한다. **문서로 만들지 않는다** — `주차계획` → `tasks/` 위에 층을 하나 더 얹으면 세 문서가 갈라진다.

### push 할지 말지

| 상황 | 어떻게 |
|---|---|
| 하위 단계 하나를 끝냈고 `main`이 안 깨진다 | **커밋 + push** |
| 항목이 반쯤 됐고 지금 올리면 `main`이 깨진다 | **커밋만. push 보류** — 작업은 로컬에 안전하다 |
| 이틀 넘게 걸린다 / 원격 백업·중간 공유가 필요하다 | **작업 브랜치**를 판다 |

**브랜치는 주차 계획에 적히지 않는다.** 계획서는 "무엇을 만드나"이고 브랜치는 "어떻게 올리나"다. 작업하다 위 셋째 줄에 해당하면 그때 판단한다.

**단계마다 브랜치를 파지 않는다.** 리뷰어가 없어 브랜치→머지가 순수 의식이 되고, 하루에 몇 번씩 하면 리듬만 끊긴다.
참고로 **W1에는 브랜치가 필요한 항목이 없다** — 가장 긴 것이 이미지 벤치 2일, 목 서버 1.5일이다. 다만 스캐폴딩 중간 상태는 `main`을 깨뜨리므로 둘째 줄(커밋만, push 보류)에 해당한다.

```bash
git switch -c work/api-scaffold      # 이틀 넘는 작업만
# ... 여러 세션에 걸쳐 커밋 ...
git switch main && git merge --ff-only work/api-scaffold && git push
git branch -d work/api-scaffold
```

> ### ⚠️ 브랜치는 세션이 아니라 **트리**에 걸린다
>
> **`git switch` 를 치면 나머지 두 세션도 함께 끌려간다.** 워킹 트리가 하나라 체크아웃된 브랜치도 하나뿐이다(3-1). `api/` 세션에서 브랜치를 파면 그 순간 `web/`·PM 세션이 보던 파일이 발밑에서 통째로 갈린다 — **세션별 브랜치는 이 구조에서 불가능하다.**
>
> 그래서 브랜치를 팔 때는:
>
> 1. **다른 세션에 진행 중인 작업이 없어야 한다.** `git status` 가 깨끗한지 본다 — 커밋 안 된 변경이 있으면 브랜치를 넘나들며 딸려 다닌다
> 2. **다른 세션에 알린다.** 같은 사람이어도 세션은 자기가 어느 브랜치에 있는지 모른 채 계속 일한다
> 3. **끝나면 `main` 으로 돌아온다.** 브랜치에 머문 채 다른 세션이 커밋하면 그 커밋이 작업 브랜치에 쌓인다
>
> 조율이 필요하다는 뜻이고, **그게 PM 세션 몫이다** (3-1 「세션끼리 말을 주고받는다」).

## 4. 시나리오

### PM — 이번 주차 계획을 세운다

주가 시작될 때 가장 먼저 하는 일이다. **이걸 건너뛰면 백로그와 실제 작업이 끊기고, 모자 셋이 각자 다른 것을 만진다.**

```bash
cd geulmoheom && git pull && claude -n gm-pm      # ← 루트에서
```
```
> /plan-week                  # 인자를 비우면 다음 주차를 스스로 판단한다
```

주차 번호는 **`MVP_PRD.md` 8장 「주차」 열**에서 온다. 지금이 몇 주차인지 셀 필요 없다 — 명령어가 `docs/주차계획/`을 보고 제안한다. 건너뛰거나 되돌아갈 때만 `/plan-week W3` 처럼 명시한다.

명령어가 이 순서로 진행한다.

0. **이미 그 주차 계획이 있으면 덮어쓰지 않는다.** 차이만 보고한다 —
   「진행 현황」 표와 PM 체크박스는 진척 기록이라 절대 날리지 않는다
1. **진척 보고** — `백로그.md`·PRD 8장·9장·`검증가설_성공지표.md`·`docs/api/미결.md`를 읽고,
   `ls web api`·`git log`로 **말이 아니라 실제로** 무엇이 됐는지 확인한다
2. **범위 초안** — 항목 · 코드 · 담당 · 선행 · 완료 조건 · 크기(S/M/L) 표
3. **과부하 지적** — **가용량은 1인분이다**(모자 셋을 한 사람이 쓴다). 과하면 그렇다고 말하고 덜어낼 후보를 제안한다
4. **대표 확인** ← 여기서 멈춘다. **무엇을 하고 무엇을 미룰지는 대표의 결정이다** — PM이 자기 범위를 자기가 승인하면 게이트가 사라진다 (1장 「대표 몫」)
5. 확인 후 `docs/주차계획/W1.md` 작성 (범위·담당·선행·완료 조건·「하지 않는 것」·「진행 현황」 빈 절)

```bash
git add docs/주차계획/ && git commit -m "W1 주차 계획" && git push
```

**`api/tasks/`·`web/tasks/`는 PM 세션이 만들지 않는다.** 각 패키지 세션에서 `/my-week`으로 만든다 — 모자가 다르다.
**대표에게 계획 링크를 보낸다** — 알림 장치가 없다.

**계획을 세울 때 지켜지는 것**

- **범위는 지어내지 않는다.** 모든 항목이 `백로그.md`의 코드(A0-2, E-3, F-3…)로 추적된다.
  백로그에 없는 것을 넣으려면 **`비전.md` 4장 질문 5개**를 먼저 통과해야 한다
- **「하지 않는 것」 절을 비우지 않는다.** 뺀 것과 이유를 적지 않으면 범위가 조용히 늘어난다
- **가용량은 1인분이다.** 모자가 셋이어도 사람은 하나다. PM 업무·백엔드·프론트가 **같은 시간을 나눠 쓴다** — 예전의 "2인분으로 잡지 마라"보다 훨씬 세게 적용된다
- **선행 관계가 자기 자신에게 걸린다.** 예전에는 백엔드 목 서버가 늦으면 프론트가 *다른 사람*이라 병렬로 놀 수 있었다. 이제 둘 다 같은 사람이라 **직렬이다.** 「A가 끝나야 B」로 짠 주차는 그 합만큼 걸린다
- **완료 조건은 검증 가능하게.** "구현한다"가 아니라 "무엇이 되면 끝인가" —
  가능하면 기계가 판정하는 것으로 (`make contracts` 성공, 테스트 통과, 응답 확인)
- **담당이 「공동」인 항목은 양쪽 「작업 쪼갬」에 모두 넣는다.** 한쪽에만 있으면 나머지 쪽 몫은
  담당자가 없어 조용히 빠진다. "결정 참여"라고만 쓰지 말고 각자 무엇을 맡는지 갈라 적는다

**주 중에 계획이 틀어지면 문서를 고친다.** 실제와 어긋난 채 방치하면 계획 문서가 죽고,
그다음 주부터 아무도 안 본다. `MVP_PRD.md` 8장이 상위이므로, 어긋남이 주차를 넘어가면 8장도 함께 고친다.

### PM — 하루를 연다 (5분)

PM 세션에서 아침마다 돌린다.

```bash

git log -p --since=yesterday        # 어제 세 세션이 무엇을 했는지
```
```

```

`/progress-week`이 각 패키지 `tasks/`를 읽어 계획의 「진행 현황」을 갱신하고, **막힌 것**(선행 미완으로 후속 대기)과 **계획 이탈**(계획에 없는 항목이 `tasks/`에 생김)을 함께 짚는다. 갱신됐으면 커밋한다.

```bash
git add docs/주차계획/ && git commit -m "W1 진행 현황 갱신" && git push
```

### PM — 문서를 고친다

개발 세션에서 명세가 틀린 것을 발견해도 **거기서 고치지 않는다.** PM 세션으로 넘긴다 — 개발 세션이 `SendMessage`로 보내거나(3-1), 직접 옮겨 적어도 된다.

```bash
cd geulmoheom && git pull && claude -n gm-pm      # ← 루트에서
```
```
> api 세션에서 올라온 것: 오류 코드표에 INTERNAL_ERROR(500)가 없어서
  미처리 예외가 프레임워크 기본 형식으로 나간다. docs/api/공통규약.md 에 반영해줘.
  용어사전 아이 화면 열 확인하고.
```
```bash
git add docs/api/
git commit -m "명세: 오류 코드표에 INTERNAL_ERROR(500) 추가"
git push
```

**경로를 명시해서 `git add` 한다** (3-1장). 개발 세션이 동시에 코드를 만지고 있다.
**문서 반영은 언제나 코드와 별도 커밋**이다. 같은 사람이라 섞을 수 있지만, 섞이면 "이 명세는 왜 바뀌었나"를 못 찾는다 — **막아주는 구조가 없고 규율뿐이다.**

### PM — 새 요청을 거른다

기능 추가 요청이 들어오면 PM 세션에서 그대로 던진다. 루트 `CLAUDE.md`가 읽혀 있으므로 Claude가 자동으로 **`비전.md` 4장 질문 5개**에 비춰보고, 하나라도 "아니오"면 먼저 알린다. 5장 「하지 않을 것」에 해당하면 이유와 대안을 낸다.

통과했다면 순서가 있다.

1. `백로그.md`에 항목으로 등록 (코드 부여)
2. 새 말이 나왔으면 `용어사전.md`에 먼저 등록
3. 그다음 주차 계획에 넣는다

**이 순서를 건너뛰면** 코드·문서·아이 화면에서 서로 다른 말이 굳고, 백로그에 없는 일이 계획에 들어온다.

### PM — 주를 닫는다

```

> docs/주차계획/W1.md 의 완료 판정 항목을 실제 저장소 상태와 대조해줘.
```

**체크박스를 믿지 말고 기계로 확인한다** — `make dev`, `make contracts`, CI `all-green`. 어긋났으면 계획 문서를 고치고, 어긋남이 주차를 넘어가면 `MVP_PRD.md` 8장도 함께 고친다.

그다음 `/plan-week W2` 로 다음 주를 연다.

### PM 모자만 지는 책임

**같은 사람이 쓰지만 모자가 다르다.** 아래는 `api/`·`web/` 세션에서 하지 않는다 — 루트 PM 세션에서만 한다.

| | 왜 PM 모자인가 |
|---|---|
| **`docs/` 전부** | 개발 세션에서 고치면 명세 변경이 코드 diff에 묻힌다. 반영 근거가 사라진다 |
| **용어사전 관문** | 새 말은 사전에 먼저. 안 하면 코드·문서·화면에서 다른 말이 굳는다 |
| **비전 4장 게이트** | 기능 추가를 거르는 유일한 장치다. **판정은 대표 몫**(1장) — PM은 게이트에 올리는 것까지 |
| **주차 계획** | 백로그와 실제 작업을 잇는 자리. **범위 확정은 대표 몫**(1장) |

**1인이 되면서 이 구분이 더 중요해졌다.** 모자가 갈리지 않으면 "명세가 불편해서 명세를 고친다"가 아무 저항 없이 일어난다. 예전에는 소유가 갈려 있어 구조가 막아줬지만 이제는 규율뿐이다.

**명세가 바뀌었으면 PM 세션에 넘긴다** (`SendMessage`, 3-1). 여기서 `docs/`를 고치지 않는다.

**API가 모자라 막히면 `api/` 세션으로 넘어간다.** 요청 문서를 쓰지 않는다 — 같은 사람이라 왕복이 성립하지 않는다(`api-requests/`는 휴면). 다만 **그 자리에서 web 세션으로 api를 고치지 않는다.** 모자를 바꿔 `api/` 세션에서 고치고, 돌아와 `make contracts` 를 다시 돌린다.

`docs/`는 이 세션에서 건드리지 않는다. 명세가 틀렸으면 **PM 세션**에서 고친다.

## 4-1. 생성물은 명령을 가진 쪽이 커밋한다 (2026-09-07)

**`web/src/api/types.gen.ts` 는 `web/` 안에 있지만 프론트가 쓰는 파일이 아니다.** `make contracts` 가 api 의 `/openapi.json` 에서 만들어내는 **생성물**이고, 그 명령은 백엔드 몫이다 (`api/README.md` 7절).

**명세를 바꾼 백엔드가 같은 자리에서 재생성하고 커밋한다.** 세션 경계를 넘는 것처럼 보이지만 아니다 — 경계 규칙이 막으려는 것은 **① 남의 반쯤 된 작업이 딸려 들어가는 것** ② **명세 변경이 코드 diff 에 묻히는 것** 둘인데, 생성물 재생성은 **사람이 판단할 내용이 없어** 둘 다에 해당하지 않는다. 오히려 프론트에 넘기면 **무엇이 왜 바뀌었는지 모르는 diff 를 프론트가 커밋하게 된다.**

- **한 파일만 담는다** — `git add web/src/api/types.gen.ts`
- **명세를 바꾼 커밋과 별개 커밋**으로 한다
- **손으로 고치지 않는다.** 어긋나면 `make contracts` 를 다시 돌린다

## 5. 관통하는 규칙

| 규칙 | 왜 |
|---|---|
| 대표 몫(1장)은 **올리고 기다린다** | 도메인·결제·주차 범위·비전 게이트·안전 정책. 나머지는 정하고 사후에 알린다 |
| `main`에 반쯤 된 것을 올리지 않는다 | 공용 작업대다. `api`가 깨지면 프론트의 `make contracts`가 실패한다 |
| **파일 상태 ≠ 실제 상태** | `done/`은 사람의 주장, `make contracts` 성공은 기계의 보증. 어긋나면 코드가 맞다 |
| 커밋 메시지에 **「명세 변경:」** 줄 | PR 본문도 이슈도 없다. 커밋 메시지가 유일한 기록이다 |
| 논의 결과를 **파일 본문에** 적는다 | 말로 정한 것도 적지 않으면 3주 뒤 근거가 사라진다 |
| 커밋 전 Claude에게 `git diff` 검토 요청 | **1인 체제에서 남은 유일한 리뷰다.** 교차 검토가 없다 |
| 하루 시작에 `git log -p --since=yesterday` | 어제 세 세션이 무엇을 했는지 아는 유일한 경로 |
| **하위 체크박스 하나 = 세션 하나** | 한 세션에서 크게 하면 컨텍스트가 늘어져 규칙 위반이 뒤로 갈수록 늘어난다 |
| 진척은 **그 모자의 패키지 `tasks/`**에 체크한다 | 세션 셋이 한 파일을 고치면 `main` 직접 push 체제에서 push 거부가 잦다 |
| **할 일은 주차 계획에서만 고른다** | `docs/api/미결.md`는 판단 기준 모음이지 할 일 목록이 아니다 |
| 주차 계획이 실제와 어긋나면 **문서를 고친다** | 방치하면 계획 문서가 죽는다. 어긋남이 주차를 넘어가면 PRD 8장도 함께 |
| **`git add -A` · `commit -am` 금지** | 위치와 무관하게 워킹 트리 전체를 담는다. 다른 모자의 작업이 딸려 들어간다. `git add .` 는 패키지 안에서 안전 |
| **push 전 `git log origin/main..HEAD`** | 커밋을 나눠도 push는 공유된다. 다른 세션의 로컬 커밋이 함께 올라간다 — 반쯤 된 것이면 `main`이 깨진다. **전부 자기 커밋이라 눈으로 읽는 것 말고 장치가 없다** (3-1) |

## 6. 슬래시 명령어

`.claude/commands/` 에 있다. 저장소에 커밋되어 세 세션 어디서나 쓴다.
**무엇을 어떻게 하는지는 각 명령어 파일이 진실이다.** 여기는 언제 누가 쓰는지만 적는다.

| 명령 | 어느 세션 | 언제 |
|---|---|---|
| `/plan-week` | PM (루트) | **주 시작** — 이번 주 범위를 정한다 |
| `/my-week` | `api/` · `web/` 각각 | **주 시작** — 계획에서 그 모자 몫을 뽑는다 |
| `/progress-week` | PM (루트) | **매일** — 진행 현황을 모은다 |
| ~~`/api-check`~~ | — | **휴면** (`api-requests/`와 함께, `adr/0008`) |

인자는 주차 번호(`W1`). `/plan-week` 은 비워도 된다 — 다음 주차를 스스로 판단한다.
`/my-week` 은 **그 패키지 안에서** 실행한다. 모자를 경로로 판별하기 때문이다 — 루트에서 돌리면 어느 모자인지 되묻는다.

**이름에 `-week` 접미어를 둔 이유** — 짧은 `/plan` 은 Claude Code 내장 plan mode와 겹쳐 가려진다.
`/status`·`/progress` 도 같은 위험이 있어 피했다. **새 명령어를 만들 때 짧고 흔한 이름을 쓰지 않는다.**

## 7. 지금 없는 것

솔직히 알고 있어야 할 한계다.

- **PR·코드 리뷰 없음.** `main`에 직접 push한다. 막는 장치가 없다
- **교차 검토가 없다.** 개발자가 1인이라 남의 눈이 코드를 보지 않는다. 남은 장치는 5장의 「커밋 전 `git diff` 검토 요청」 하나뿐이다
- **브랜치 보호 없음.** 비공개 무료 플랜이라 쓸 수 없다. `.github/CODEOWNERS`는 책임 소재 기록으로만 남아 있고 아무것도 강제하지 않는다
- **대표에게 가는 알림이 없다.** 세션끼리는 메시지를 주고받지만(3-1), **대표는 그 경로에 없다.** 「대표 몫」(1장)은 사람이 직접 말해야 한다
- **CI는 사후 통보.** `main` push 후에 돌아서, 깨진 코드가 이미 들어간 다음 빨간불이 뜬다
- **버스 팩터가 1이다.** 제품 지식이 한 사람에게 모인다. 사람이 빠지면 남는 건 `docs/`·ADR·`미결.md` 뿐이라 **문서를 SSOT로 유지하는 규약이 예전보다 중요하다**

**PR을 열지 않는다.** 리뷰어가 0명이라 순수한 의식이 된다(`adr/0004`). 아래 셋일 때는 **PR 대신 대표에게 알리고**, 브랜치는 3-3 기준(이틀 넘는 작업)으로만 판단한다.

1. 계약이 바뀔 때 (엔드포인트·응답 스키마) — 커밋 메시지에 「명세 변경:」 줄이 유일한 기록이다
2. Claude가 크게 지어낸 것 (파일 5개 이상, 200줄 이상) — 커밋 전 `git diff` 검토를 반드시 건다
3. 안전·프라이버시 경로 (Moderation, PII 마스킹, 로깅) — **「대표 몫」이다**(1장)
