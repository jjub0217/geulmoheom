## 1. 삽화 도착 통지 — 폴링 vs SSE

**제안**: 폴링 우선, SSE는 SHOULD (`GET /artworks/{artwork_id}`)

**결정 기준**
- W1 이미지 모델 벤치의 **실제 생성 지연**. 3초 안쪽이면 폴링으로 충분, 10초를 넘으면 대기 화면 설계가 달라진다
- 아이가 기다리는 동안 보는 화면이 무엇인지 (가이드 캐릭터 대사로 메울 수 있는 길이인가)
- 폴링 간격·타임아웃·실패 시 재시도 횟수를 여기서 같이 정한다

**담당**: 백엔드(엔드포인트) + 프론트(대기 UX) · **기한**: W1

---

## 2. 클라이언트 PII 정규식 목록 배급

**제안**: 백엔드가 JSON으로 제공 → 프론트가 로드 (`GET /config/pii-patterns`)

**결정할 것**
- 엔드포인트를 신설할지, 빌드 타임 상수로 박을지 (패턴이 바뀌면 프론트 재배포가 필요한가)
- 캐시 정책 — 자녀 토큰 없이도 받을 수 있어야 하는가
- **경계 명시**: 프론트 마스킹은 아이에게 주는 즉시 피드백용이고, **최종 판정은 항상 서버**다. 프론트를 우회해도 서버에서 막혀야 한다

**참조**: PRD 1.1b, `Stage0_API명세.md` 0절 원문 취급 · **담당**: 백엔드 주도 · **기한**: W1

---

## 3. 자정 기준 — 일일 상한 리셋 시점

**제안**: 클라이언트 타임존 헤더, 서버 계산

**결정 기준**
- 일일 턴 상한은 **MVP 필수 가드레일**이다. 클라이언트가 보낸 타임존을 그대로 믿으면 헤더를 바꿔 상한을 우회할 수 있다
- 대안: 서버 KST 고정 / 자녀 생성 시점에 타임존을 확정해 저장 후 변경 불가
- 밤 11시 50분에 시작한 세션이 자정을 넘길 때의 처리도 같이 정한다

**참조**: PRD 가드레일, `DAILY_CAP_REACHED` (409) · **담당**: 백엔드 · **기한**: W1

---

## 4. 토큰 저장 위치

**제안**: 자녀·학부모 모두 HttpOnly 쿠키

**결정 기준**
- 자녀 토큰은 **30일 유효**이고 접속 코드 교환으로 발급된다. 탈취 시 영향이 크다
- PWA·iOS Safari에서 HttpOnly 쿠키 제약 확인 필요 (홈 화면 추가 시 쿠키 유지, ITP)
- 두 토큰은 역할이 다르고 상호 대체 불가 — 쿠키 이름·경로를 분리할지
- 크로스 오리진 여부(web:3000 ↔ api:8000)에 따라 `SameSite`·CORS 설정이 갈린다

**참조**: `Stage0_API명세.md` 0절 인증 · **담당**: 백엔드 + 프론트 공동 · **기한**: W1

## 5. 스테이징 목 응답 서버

**제안**: 백엔드가 `Stage0_API명세.md` 그대로 **W1 3일차까지** 목 응답 서버 제공 → 프론트 병렬 개발

이건 결정이 아니라 **산출물**이다. 완료 조건:
- [ ] 명세의 모든 엔드포인트가 고정 응답을 반환
- [ ] `POST /attempts`의 `outcome` 3분기(`result` / `scaffold` / `blocked`)를 요청 파라미터로 강제 가능
- [ ] `/openapi.json`이 뜬다 (프론트가 `make contracts`를 돌려볼 수 있어야 함)
- [ ] 오류 응답 — 최소 `DAILY_CAP_REACHED`(409), `VALIDATION_ERROR`(422), `UNAUTHORIZED`(401)

**담당**: 백엔드 · **기한**: W1 3일차
