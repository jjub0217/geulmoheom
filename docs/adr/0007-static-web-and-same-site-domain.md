# 0007 — web을 정적 빌드로 배포하고, api를 같은 등록가능 도메인 아래 둔다

날짜: 2026-09-06 · 상태: 채택 · **`MVP_PRD.md` 1.5절과 `아키텍처 및 구현난의도.md` 2장의 「단일 컨테이너 배포」를 대체함** · `docs/api/미결.md` 11-5를 닫음

## 맥락

PRD 1.5와 아키텍처 2장은 배포를 **"단일 컨테이너 (Fly.io / Railway 급)"** 라고만 적었다. 그런데 스택은 **Next.js(Node) + FastAPI(Python) 두 런타임**이다. 그 한 컨테이너 안에 무엇이 들어가는지를 아무 문서도 말하지 않았다.

두 갈래에서 독립적으로 같은 지점에 도달했다 — ① 프론트가 자기 스택에 Node가 왜 필요한지 따라가다 ② 백엔드가 미결 11-2(토큰 저장)의 쿠키 설계를 짜다. 그래서 11-5가 **11-2보다 먼저 정해야 하는 것**으로 신설됐다(2026-09-04).

세 가지가 걸려 있다.

- **프로덕션에 Node 서버가 필요한가** — Next.js App Router는 기본이 서버 렌더링이다
- **배포처가 어디인가** — 정적 빌드(`output: 'export'`)는 Next의 `headers` 설정을 지원하지 않는다. 지금 서비스워커는 Next가 붙이는 `Service-Worker-Allowed: /` 덕에 `scope: "/"` 가 성립한다
- **api를 web과 같은 등록가능 도메인 아래 두는가** — 이것이 11-2의 가장 어려운 부분을 없앤다

프론트(@jjub0217)가 2026-09-06 `web/tasks/W1.md`에 답을 냈고, 백엔드 서버안은 `api/notes/미결11-2_토큰저장_서버안.md`에 있다.

## 결정

1. **web은 정적 빌드로 배포한다.** 프로덕션에 Node 서버를 두지 않는다. 「단일 컨테이너」에는 **api만** 들어간다
2. **배포처는 Cloudflare Pages**
3. **호스트를 3단으로 나눈다. 셋 다 같은 등록가능 도메인이다**

   | 호스트 | 무엇 |
   |---|---|
   | `geulmoheom.app` | 랜딩 (F-2 Fake Door → 마케팅) |
   | `app.geulmoheom.app` | web PWA |
   | `api.geulmoheom.app` | api |

   **도메인 문자열은 등록 가능 여부를 확인하지 않았다.** 여기서 정한 것은 *모양*(같은 등록가능 도메인 + 서브도메인 3단)이고, 실제 문자열은 레지스트라 확인 후 확정한다

   **레지스트라 확정: Cloudflare Registrar (2026-09-07, 대표).** 가격이 아니라 기술 제약이 정했다 — **`api.` 를 프록시 뒤에 세울 수 있어야 Safari 16.4+ IP 휴리스틱을 피한다**(`공통규약.md` 「수명」). Cloudflare 는 자기 서비스가 아닌 원본(Fly.io/Railway)도 프록시할 수 있고, Vercel·Netlify 는 자기 배포물 앞에만 선다. R2 가 이미 Cloudflare 라 계정·청구서·DNS 존이 한 곳으로 묶이는 것은 덤이다.
   **등록 직후 할 것** — ① `app.`·`api.` **둘 다** 프록시 켜기(하나만 켜면 IP 가 갈려 문제가 그대로 남는다) ② `dig` 로 두 호스트의 IPv4 앞 16비트 공유 실측. **②가 30일 토큰의 유일한 확정 증거다**
4. **`next/image` 는 Stage 0에서 `unoptimized: true`.** W3 B-3에서 다시 보지 않는다
5. **서비스워커 배치는 프론트가 정한다** — `_headers`(Pages 지원)로 갈지, `public/sw.js` 로 옮겨 오리진 루트에서 서빙해 헤더 의존을 아예 없앨지

## 근거

- **Stage 0·1 어디에도 SSR이 필요한 화면이 없다.** 태블릿 PWA고, 인증은 쿠키라 브라우저가 알아서 붙이고, 데이터는 19개 엔드포인트 전부 클라이언트 fetch다. Stage 1의 GM 서사 스트리밍도 FastAPI에서 나오지 Next에서 나오지 않는다
- **"나중에 SSR이 필요해지지 않는가"에 대한 답도 아니오다.** 유일한 후보가 P1 또래 공유 서재의 공개 책 페이지인데, **아이 창작물이 검색에 잡히는 것은 사이버 안전 문제**라 애초에 원하지 않는 것이다(비전 5장). SEO가 요구사항이 아니면 SSR을 되살릴 이유가 없다
- **정적 빌드가 오히려 「단일 컨테이너」의 의도에 더 가깝다.** 그 결정의 목적은 파일럿 규모에서 운영 표면을 줄이는 것이었다. 한 컨테이너에 Node와 Python을 같이 넣는 것은 단순한 게 아니라 런타임 두 개를 한 프로세스 트리에서 굴리는 것이다
- **R2가 이미 Cloudflare다.** 스토리지·웹 호스팅·DNS가 한 계정, 한 대시보드, 한 청구서로 묶인다. 무엇보다 **DNS 존이 같아져서 결정 3이 공짜로 따라온다** — `api` 서브도메인을 Fly.io/Railway로 CNAME 거는 것이 한 줄이다
- **cross-site로 가면 자녀 30일 토큰이라는 설계가 깨진다.** iOS ITP가 3rd-party 쿠키를 막으면 아이가 앱을 열 때마다 접속 코드를 다시 넣어야 한다. E-3/E-4에 재인증 흐름이 **추가되는** 정도가 아니라 PRD의 「30일」이 성립하지 않는다
- **web을 apex에 두지 않는 이유는 F-2다.** 랜딩을 apex에 올려두고 나중에 앱이 그 자리를 차지하면 web 오리진이 바뀌고, 그때 쿠키·서비스워커 스코프를 다시 잡아야 한다. 지금 나누면 same-site가 유지되고 PWA 서비스워커 스코프가 마케팅 사이트 캐시와 섞이지 않는다. **지금은 공짜고 나중엔 비싸다**
- **`.app` 은 HSTS 프리로드 TLD라 HTTPS가 강제된다.** 아동 제품에는 이점이다

## 대안

- **Next를 Node 서버로 컨테이너에 넣는다** (8/29 문서의 문언 그대로) — SSR 여지를 남긴다는 것이 유일한 우위인데, 그 여지가 필요해질 시나리오가 위에서 닫혔다. 대가는 런타임 하나를 계속 운영·패치하는 것이다
- **Vercel / Netlify** — 헤더는 넣을 수 있다. 그런데 벤더가 하나 더 늘고, R2와 계정이 갈리고, 결정 3의 DNS 작업이 두 곳으로 나뉜다. 이길 근거가 없다
- **web·api를 서로 다른 도메인에 둔다** — `SameSite=None` + ITP 우회 설계가 필요하다. 우회할 방법이 마땅치 않다는 게 문제의 핵심이다
- **web을 apex(`geulmoheom.app`)에, 랜딩을 서브도메인에** — 마케팅 관례상 apex가 랜딩인 편이 자연스럽고, F-2가 먼저 뜨므로 순서상으로도 맞다

## 결과 — 감수하는 것

- **배포 대상이 둘이 된다** (Pages + api 컨테이너). 다만 Pages는 git 연동이라 실질 작업량은 늘지 않는다
- **정적 export의 제약을 계속 진다.** Next의 `headers`·`redirects`·미들웨어를 쓸 수 없다. 필요해지면 배포처의 `_headers`로 내려간다 — **배포처를 옮길 때 이 파일이 함께 옮겨져야 한다**
- **`next/image` 최적화를 포기한다.** Stage 0은 카드당 삽화 1장, 1024x1024, 태블릿 표시라 최적화가 벌어주는 것이 없다. 삽화 수가 늘거나 목록 화면이 생기면 다시 본다
- **Google(LLM·이미지) 위에 Cloudflare(스토리지·웹·DNS)가 더해진다.** 벤더가 둘로 정리되는 것이지 늘어나는 것은 아니다
- **도메인 문자열이 아직 없다.** 등록 전까지 이 ADR의 호스트 표는 예시다. **F-2 Fake Door가 도메인을 필요로 하므로 이것이 다음 차단 지점이다**

## 재검토 시점

- **공개 책 페이지에 SEO가 필요해질 때** — 그때는 SSR이 아니라 **아이 창작물을 검색에 노출할 것인가**를 먼저 다시 판단한다(비전 4장 질문 5개)
- ~~**Cloudflare Pages가 `_headers` 없이 서비스워커 스코프를 못 잡을 때** — `public/sw.js` 배치로 내려간다~~
  **2026-09-07 닫혔다 — 시험하지 않고 바로 `public/sw.js` 로 갔다** (`da6bdea`). 이 줄은 「Pages 가 못 잡으면」을 조건으로 걸었는데, **조건을 기다릴 이유가 없었다.**
  `public/sw.js` 는 오리진 루트에서 서빙되어 **헤더가 아예 필요 없다** — 「헤더를 붙일 수 있는가」라는 질문 자체가 사라진다. `_headers` 는 **호스트를 옮기면 조용히 무효**가 되는데 이쪽은 배포처를 안 따라다닌다.
  **실측**: `out/sw.js` 가 루트에 · 정적 서버에서 `/sw.js` 200 · **`Service-Worker-Allowed` 없이 scope `/`**. `output: "export"` 와 **같은 커밋**에 넣었다 — 따로 가면 둘 중 하나만 들어가고 그때 배포가 깨진다.
  **정적 export 로 못 쓰게 된 것 넷**: `headers()` · `redirects()` · `rewrites()` · 미들웨어. 필요해지면 그때 `_headers` 로 내려간다
- **api를 같은 도메인에 못 둘 사정이 생길 때** — 11-2 쿠키 설계와 E-3/E-4 재인증 흐름을 통째로 다시 짠다. **이 ADR에서 가장 비싼 되돌림이다**
