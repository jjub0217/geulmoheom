대상 주차: **$ARGUMENTS** (비어 있으면 `docs/주차계획/`에서 가장 최근 것)

## 어느 역할인가

- !`pwd`
- 경로가 `api/` 안이면 **백엔드**, `web/` 안이면 **프론트**다. 저장소 루트에서 실행됐거나 판단이 안 서면 **먼저 물어라.**
- 대상 파일은 그 패키지의 `tasks/$ARGUMENTS.md`

## 읽을 것

- !`git pull --rebase -q 2>&1 | head -3; ls docs/주차계획/ 2>/dev/null`
- `docs/주차계획/$ARGUMENTS.md` — **계획. 이것이 유일한 출처다**
- 그 패키지의 `tasks/README.md` — 이 폴더의 규칙

## 할 일

**1. 계획에서 내 역할의 「작업 쪼갬」 항목을 가져온다.** 「범위」 표에서 담당이 내 역할인 행의 **완료 조건**도 함께 본다.

**「범위」 표와 「작업 쪼갬」을 대조한다.** 담당이 `공동`이거나 내 역할인 행이 「작업 쪼갬」의 내 절에 없으면 **계획의 누락**이다. 체크리스트에 임의로 만들어 넣지 말고 **PM에게 말하라고 알린다** — 계획을 고치는 것이 먼저다.

**2. 이미 `tasks/$ARGUMENTS.md` 가 있으면 덮어쓰지 않는다.**
계획과 대조해 **차이만 보고**하고, 어떻게 할지 사용자에게 묻는다.
- 계획에 있는데 파일에 없는 항목 → 추가할지
- 파일에 있는데 계획에 없는 항목 → **범위가 조용히 늘었다는 뜻.** 지울지 PM에게 말할지
- **이미 `[x]` 인 항목의 체크는 절대 지우지 않는다**

**3. 없으면 만든다.** 형식:

```markdown
# $ARGUMENTS — <역할> 진척

계획: `docs/주차계획/$ARGUMENTS.md` 「작업 쪼갬 · <역할>」 · 소요·상세는 그쪽에 있다
**범위를 여기서 바꾸지 않는다.** 계획이 틀렸으면 PM에게 말한다.

- [ ] **1. 항목 제목** — 핵심 키워드만
  - [ ] 완료 조건이 여럿이면 하위 체크박스로

## 메모

<!-- 작업 중 알게 된 것. 계약·설계 결정은 여기가 아니라
     docs/api/미결.md 또는 api-requests/ 로 간다 -->
```

**4. 옮길 때 지킬 것**

- **소요 시간·상세 설명을 옮기지 않는다.** 계획에 두고 여기는 체크박스와 키워드만. 옮겨 적을수록 두 문서가 갈라진다
- 항목 번호는 계획과 맞춘다
- **크기가 M·L인 항목은 하위 체크박스로 쪼갠다. 이것이 가장 중요하다.**
  기준은 **하나가 Claude 세션 하나 분량(반나절 이하)이고, 각각 독립적으로 커밋 가능할 것**.
  큰 작업을 한 세션에서 하면 컨텍스트가 늘어져 품질이 떨어진다. 쪼갠 단위마다 세션을 새로 띄운다.
  - 예: api 스캐폴딩(M) → ① uv + pyproject + ruff/pytest ② FastAPI 뼈대 + `app.main:app` ③ SQLAlchemy(async) + Alembic 초기 마이그레이션
  - 예: 목 서버(M) → ① 엔드포인트 고정 응답 ② `outcome` 3분기 파라미터 ③ 오류 3종 ④ `make contracts` 확인
  - **쪼갤 수 없는 것은 쪼개지 마라.** 억지로 나누면 절반만 돌아가는 커밋이 나온다
- 범위 표의 완료 조건이 여럿이면 그것도 하위 체크박스에 반영한다
- **선행이 있는 항목에는 그 사실을 적는다** (예: "선행: 백엔드 목 서버. `done/`이 아니라 타입 생성이 착수 신호")
- **끝낸 뒤 상대에게 말해야 하는 항목**에는 `- [ ] 상대에게 직접 말했다` 를 하위에 넣는다. 알림 장치가 없어 가장 자주 빠진다
- 계획에 없는 항목을 **지어내지 않는다**

**5. 커밋을 제안한다** (실행은 사용자에게 맡긴다)

```
git add <패키지>/tasks/ && git commit -m "$ARGUMENTS 체크리스트" && git push
```

경로를 명시한다 — `git add -A` 를 쓰지 않는다 (`docs/작업흐름.md` 3-1).
